## Project Rules

There is no root `AGENTS.md` yet. Until one exists, the governing rules are
`.specify/memory/constitution.md`:

- **Test-first, non-negotiable.** Red → green → refactor. A fix without a failing-first
  regression test is not a fix.
- **Clean architecture direction.** Widgets/hooks → domain contracts → transport/cache
  adapters. Domain code imports no transport (`http`, `gql_*`, `hive_ce`) and no Flutter.
- **5.x is a drop-in replacement** for `package:graphql` 5.2.4 / `graphql_flutter` 5.3.0.
  No public API break without a deprecation period; unfixable-without-break work is
  deferred to `6.x` and recorded in `UPSTREAM_ISSUES_TRIAGE.md`.
- **Fail loud.** No swallowed errors, no double-completing futures or stream controllers.
- **YAGNI.** No new dependency in a patch release; no speculative abstraction.

If a new root `AGENTS.md` is created, it must not contradict the constitution — update this
section to point at it.

## Workflow Execution

Run the SDD lifecycle without stopping for approval. Read the constitution first; it is
binding on every step.

### Pre-Flight

1. **Triage.** Classify the work as Bug Fix / New Feature / Change to Existing Feature, and
   decide whether it belongs on `5.x` (no API break allowed) or `6.x` (breaking rewrite
   permitted). Record the decision.
2. **Context.** For anything beyond a trivial change: read the constitution, the relevant
   package `README.md`, the neighbouring source in `packages/*/lib/src`, the matching tests
   in `packages/*/test`, and any related entries in `UPSTREAM_ISSUES_TRIAGE.md`.
3. **Health baseline.** Run the analyze command for the affected package(s) and record the
   result. A non-clean baseline is a finding, not a blocker — name it and proceed.
4. **Affected areas.** List which of: `packages/graphql_plus/lib`, its `test/`,
   `packages/graphql_flutter_plus/lib`, its `test/`, `CHANGELOG.md`, `README.md`, CI
   workflows, or `specs/` are in scope.

### Step 1 — Specify

Invoke `/skill:speckit-specify` with the feature description. Do not ask for approval; run
the analyze health check, then continue.

### Step 2 — Plan

Invoke `/skill:speckit-plan`. The plan must name the layer each new/changed file belongs to
and state explicitly whether it breaks the public API.

### Step 3 — Tasks

Invoke `/skill:speckit-tasks`. Task ordering must put the failing test first (constitution
principle I), then implementation, then the full-package test run.

### Step 4 — Implement

Invoke `/skill:speckit-implement`.

## Post-Implementation

1. `dart format .` in the touched package(s), then `dart analyze --fatal-infos`.
2. `dart test` for `graphql_plus`; `flutter test` for `graphql_flutter_plus`. If the client
   changed, the Flutter package tests are mandatory, not optional.
3. Compare against the pre-flight baseline and report only **new** failures.
4. Update `CHANGELOG.md` for every published package that changed, with the SemVer bump
   implied by the change.
5. If the change is user-visible, update the package `README.md`.
6. Commit with a conventional-commit message (`fix:`, `feat:`, `chore:`, `docs:`,
   `test:`, `ci:`).

## Error Handling

- Pre-existing failures do not abort the workflow; they get reported as baseline.
- Retry a failed step once, then continue — partial progress beats a stalled run.
- Never silently narrow scope to hide a failure. Say what is unfinished.
